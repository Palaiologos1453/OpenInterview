# 八股与项目：两条本地语义追问工作流

状态：架构设计，尚未接入运行路径。现有 LiveKit 仍使用规则引擎，不能将本设计视作已经实现的能力。

## 当前代码的限制

- `interview_engine.py::_select_followup_question` 用 rubric 缺口与分数决定追问，
  对上一题已经是 followup 的情况直接退出，同一 parent 也通常只允许一次追问。
- `_adaptive_followups` 主要拼接缺口、短回答、缺证据等模板，不能可靠地区分
  “没讲到”“明确讲错”“表达不同但正确”“需要先澄清题意”。
- `_select_question` 根据 `MODE_FLOW[turn_index]` 决定阶段，追问也消耗这个全局步数。
  因此会发生话题尚未探明就进入下一阶段，以及用下一个阶段的标签包装上一题追问的问题。
- `_score_answer` 仍使用长度、结构词、技术词等启发式分数。这些只能作为辅助信号，
  不足以承担语义理解、真实经历判断或最终能力评价。
- LiveKit 的 `LOCAL_PROVIDERS.llm` 为 mock；现有本地 LLM 适配器未进入面试决策路径。

## 目标架构

共享层负责转录版本、会话持久化、时间预算、幂等、取消、语音播放和报告。
面试导演维护当前考察目标，再把本轮交给八股或项目工作流。
两条工作流可以复用同一份本地模型权重，但分别维护输入上下文、状态、检索范围、提示词和评分锚点。

```text
最终转录 + 当前任务 + 会话状态
              ↓
          面试导演
          ↙      ↘
   八股工作流      项目工作流
   知识证据        候选人陈述与证据台账
   理解评估        经历/约束/贡献分析
   能力探查        针对性澄清与验证
          ↘      ↙
     校验决策与问题 → 提交状态 → 播报
              ↓
       独立的赛后评价与复盘
```

规则继续承担工程约束：一次一个主要问题、禁止重复、预算和阶段合法性、证据引用存在性等。
回答意味着什么、缺的是哪种理解、应该问哪一个问题，交给有上下文的本地语义模型。
不要求安装多 Agent 编排框架，更不要求同时运行两个大模型。

## 八股工作流：建立知识理解的证据

输入：当前知识点、带版本的权威资料/人工审校知识卡、已问问题、候选人回答及原句引用。

状态至少包含：

- 当前概念与前置知识。
- 已有回答支持的理解、明确错误、遗漏、尚未验证的部分。
- 已经使用的验证题、反例题和澄清问题。
- 当前深度与本主题剩余预算。

过程：

1. 提取可判断的命题，而不是关键词计数。例如“RR 下所有查询都读同一个快照”。
2. 对照资料与题目限定条件，区分错误、遗漏、正确的其他表述和识别歧义。
3. 选择最能区分理解程度的下一步：澄清术语、补前置概念、给具体执行序列、要求推导结果、
   改一个条件问边界，或在理解已经充分时换主题。
4. 每条评价引用候选人的话和知识依据；资料不足时标注不确定，不伪造标准答案。

例子：候选人说“RR 下查询始终一样”。先明确数据库/引擎与查询类型，
再给包含普通 SELECT 和 SELECT FOR UPDATE 的两事务场景让其推导。
如果已准确区分，就问边界；如果连快照与加锁的差别都不清楚，就回到前置概念。
不能因为出现“MVCC、Read View”就判定理解到位。

八股评分维度：概念正确性、机制解释、条件与边界、场景迁移。
允许表达与参考答案不同；允许通过后续澄清修正评估。

## 项目工作流：建立经历与决策的证据

输入：简历原文、分项目的候选人陈述、已确认的背景/约束、历次澄清、用户自愿提供的证据。
通用技术资料只能帮助理解机制，不能用来补写候选人的项目事实。

每个项目的状态至少包含：

- 项目名、时间线、角色、团队范围、本人职责。
- 问题与目标、规模与约束、实际方案、备选方案和取舍。
- 候选人声称的指标、统计口径、基线与归因方式。
- claim ID、原文来源、支持或冲突的陈述、尚待澄清的问题。
- 尚未说明 / 候选人自述 / 有可核对材料支持等状态。

过程：

1. 把“我们优化了缓存”拆成个人职责、具体变更和效果三个待澄清的陈述。
2. 从影响最大的未知点继续问，不按固定顺序盘问全部维度。
3. 已经说“我没负责缓存层”，就更新职责边界，不再要求其证明本人实现缓存细节。
4. 出现时间线或数据口径不一致时引用两处原话并中性澄清，不直接指控造假。
5. 对未实际发生的故障可以提出假设，但明确标注“如果……”，不能说“你们当时发生故障后……”。

例子：候选人说“我给查询加了索引，P95 从 800ms 降到 200ms”。
若尚未解释变更，就问具体 SQL 与索引设计；若机制已讲清，但效果归因不明，
就问两次测量的流量、缓存与数据量是否可比。不要转成泛泛背诵 B+ 树。

项目评分维度：问题定义、职责边界、约束下的设计取舍、实施过程、验证与复盘。
“没有展示 PR”不等于项目不真实；“简历写了”也不等于已经独立验证。
涉及保密材料时接受脱敏说明，不要求候选人泄露所在公司的信息。

## 两条工作流如何衔接

以本轮考察意图为准，不能看到 Redis/MySQL 关键词就切换模式。
项目中发现知识疑点，可以建立一个关联项目的短知识验证分支，结束后回到原项目。

例如项目声称 RR 已解决全部并发问题：

- 项目问题：实际哪个并发场景出错，候选人改了什么？
- 知识验证：给出明确的事务序列，让候选人推导行为。
- 回到项目：这个边界在原项目中如何处理或验证？

“了解原理”和“亲自实现过”记录为不同证据，不能互相替代。
追问深度由模型建议与预算共同决定，不再通过每答一次就递增阶段游标来推动流程。

## 本地模型的输出契约

使用 Ollama 等本地服务的结构化输出能力，返回经过 Pydantic 校验的短决策对象，例如：

```json
{
  "track": "project",
  "action": "clarify_metric",
  "target_claim_id": "project-1-claim-4",
  "answer_quote_ids": ["turn-3-quote-2"],
  "knowledge_refs": [],
  "assessment_status": "needs_clarification",
  "question": "你提到 P95 从 800ms 降到 200ms，两次测量的流量和数据量是否一致？",
  "state_revision": 8
}
```

短决策对象只保存可审查的结论、依据与下一步，不要求存储模型的长篇内部推理。
结构合法不代表内容正确：还要校验 claim/quote 是否存在、问题是否引入新事实、
是否重复追问、是否越过当前职责边界，并用人工标注样本验证。

知识卡需要补足正确命题、常见误区、前提/版本、参考依据和多种可接受回答。
项目台账必须保留原文与来源。只写两套 system prompt，仍然容易失忆、误判和编造。

## 与现有实时流水线的关系

现有约一秒的结果来自规则决策与提前合成，不能直接沿用为接入 LLM 后的性能承诺。

- 说话期间优先准备知识检索、项目相关陈述和待澄清草稿。
- 草稿绑定 transcript revision、session revision 和来源 ID；最后一句反转意思时撤销。
- 最终转录到达后确认结构化决策，再提交状态和播报。不能对每个 ASR 快照直接调用有写入副作用的工具。
- LLM 不是严格确定函数；当前“两个快照生成同样题目”的启发式需要重新评估。
  预备音频只能复用已经通过最终检查、且文本/上下文版本一致的那一份。
- 本地 LLM 与 ASR/TTS 共用显卡，应控制模型并发、上下文和输出预算，测量真实显存与延迟。

暂定使用同一个本地指令模型运行两个工作流。具体模型规格需要以机器显存、推理性能和
两类语义评测决定，不能仅凭参数量保证追问质量。

## 实现顺序与验收

1. 增加独立的知识理解状态与项目陈述台账，以及明确的阶段游标/主题预算。
2. 接入本地结构化决策，先通过文本对话验证两条工作流，保留可追溯的决策记录。
3. 拆分八股与项目评价量表。旧的长度/关键词评分可留作诊断，但不能冒充语义模型结论。
4. 正确性过关后再接入 LiveKit、增量检索和受控预备音频，重测端到端延迟。

至少覆盖这些对照：

- 八股：关键词相同但逻辑相反；正确的不同表述；错误前提；版本差异；答对后不重复追问；
  答错后能问到诊断性场景；ASR 将术语听错时先澄清。
- 项目：跨项目的技术不能串用；团队成果与本人工作；缺失指标不编数字；时间线冲突；
  候选人主动修正；没有做过的模块；保密限制；模糊陈述只引发验证而非真实性判决。
- 共同：问题相关性、引用准确性、事实新增错误、重复追问、修改后的状态一致性、
  长对话与超时恢复。语义质量与延迟分别报告，不用一个总分掩盖缺陷。
